# Runtime foundation and durability decision

**Status:** implementation decision for the internal foundation increment. Public contract compatibility and integrated runtime acceptance remain pending.

## Runtime and package

Use dependency-light ECMAScript modules on Node 22. The validated toolchain is Node 22.23.3 with npm 10.9.9, recorded in the read-only toolchain manifest at /Users/completetech/agent-harness/triage/agent-creative-v1/execution/node22-toolchain.json. Its official archive checksum was verified there. The .node-version file, CI, and package engines pin the validated Node 22 line; the package accepts Node >=22.23.3 <23. The EI and CE supervisors have accepted ESM with .d.ts declarations. Their conformance and producer/consumer compatibility are still pending.

The runtime uses Node's built-in node:sqlite API and adds no third-party runtime dependencies. The API is unflagged starting in Node 22.13 but remains experimental in this release. DatabaseSync operations are synchronous; its timeout option is documented since 22.16, and the additional database options used here are documented since 22.18. The module requires a file-backed database, a Node 22 runtime at or above 22.23.3, the SQLite module, and the expected API. It fails with a typed error if those checks do not pass; there is no in-memory recovery fallback. Native primary SQLite BUSY/LOCKED result codes, including extended codes, map to retryable `STORE_BUSY` without copying native messages. The store bounds each lock wait; it does not run an automatic retry loop. See the [official Node 22.23.3 SQLite documentation](https://nodejs.org/download/release/v22.23.3/docs/api/sqlite.html).

The runtime APIs used here exist by Node 22.18; this package deliberately requires the tested Node 22.23.3 patch or later within Node 22. Local tests use Node 22.23.3/npm 10.9.9. This is not evidence of the deployment server's exact Node 22 patch, SQLite build, or process/filesystem limits. Server compatibility and operational sizing remain pending. The runtime has no third-party dependencies; TypeScript 5.9.3 is pinned as a development-only compiler for the `.d.ts` consumer check. The local bootstrap supports offline npm installation when that locked compiler package is already in the npm cache. CI uses the pinned Node toolchain and lockfile.

The package root is explicitly experimental and internal. It exports typed safe errors, strict local configuration, and internal durable-store primitives. It does not export ResearchPort, CreativePort, DecisionPort, AuthorizationPort, MeteringPort, ArtifactPort, ClockPort, PlannerPort, or locally invented replacements. The maintained shared-contracts catalog at revision c4caaccc2ea63b273eeac17ed89af8ac64f6bbde describes proposed contracts and does not contain generated public bindings. Canonical bindings, fixtures, and actual EI/CE consumer signoff must arrive before a public compatibility claim.

## Data ownership and scope

| Internal record | Owner in this increment | Boundary |
| --- | --- | --- |
| Workflow state, lease, event log, outbox | agent-harness | Private persistence; callers use the experimental internal runtime |
| Checkpoint snapshot | agent-harness | Private versioned JSON envelope; it does not redefine a shared contract |
| Logical operation, billable-attempt reference, transport-attempt reference | Agent and research owns execution identity; this store records opaque identifiers | No amount, provider schema, billing result, or ledger projection is implemented |
| Authority/hold reference | External authority remains owner | Opaque reference only; lease lifecycle never releases or settles it |
| Result and artifact bytes/hash | Their producing capability remains the content owner; the harness stores an immutable internal copy/reference | Does not create an artwork approval authority or replace canonical artifact manifests |

No UI, provider adapter, dispatch code, Neatlogs integration, approval authority, financial ledger, budget reservation service, or extra service boundary is introduced. Configuration requires explicit mode, model, deadline, attempt, elapsed-time, and cost bounds. Unknown environment properties are ignored for additive compatibility; required values are never silently selected. Live mode is rejected because canonical ports and external authorities are not integrated. The image variables in .env.example state an access preference only and do not configure an engine adapter.

## Durable state and ordering

| State | Meaning and allowed handling |
| --- | --- |
| queued | Created with checkpoint sequence 1; may start or be cancelled. |
| running | A fenced worker may advance workflow-local state or persist a dispatch intent. |
| awaiting_response | An external intent is durably recorded. The store does not make the external call. |
| reconciliation_pending | An external outcome or response checkpoint needs reconciliation. Another intent is rejected. |
| review_required | Work stops for a separately owned review. No review authority is implemented here. |
| succeeded, failed, cancelled | Terminal. No later transition is accepted. |

Every state-changing writer opens an SQLite BEGIN IMMEDIATE transaction, compares the expected workflow revision and current fencing token, writes its event and outbox entry atomically, and commits. The immutable event sequence is the durable order across processes. A cancellation and completion racing from the same revision have one winner: the transaction that commits first. The second stale compare-and-swap is rejected; terminal state cannot be reversed. If an external intent already exists, cancellation records intent and moves to reconciliation instead of claiming the external effect was undone.

Lease tokens increase monotonically. A stale token or expired lease cannot write workflow state. Lease expiry or release with a persisted intent marks its outcome unknown, moves the workflow to reconciliation, and retains the opaque authority/hold reference. The store does not release that reference. No new operation attempt may be recorded until an unknown or response-received outcome is reconciled. A transport retry may be recorded only while an uncancelled workflow is awaiting the response. Cancellation and a retry from the same expected revision serialize through SQLite compare-and-swap; after cancellation is accepted, a fresh retry identity is rejected. A response for a request already dispatched before cancellation may still be recorded and reconciled. This is not a financial authorization check: dispatch remains unavailable and future integration must verify the canonical authority before any billable operation.

Response bytes, their SHA-256, any immutable result/artifact bytes, and the proposed next checkpoint are persisted as a response receipt in one transaction. The receipt stores a SHA-256 over the exact UTF-8 bytes of its proposed checkpoint JSON. Recovery checks this digest before parsing or promoting those bytes. Checkpoint advancement is a separate transaction. After a process restart, a current fenced worker can reconcile a verified receipt into the next immutable checkpoint without repeating the external operation. A durable completed receipt also gates redispatch of the same workflow-local logical operation, even if a caller supplies a new billable attempt ID. An authoritative `no_effect` receipt still permits a distinct subsequent attempt; both attempt records remain. An unknown outcome without a receipt stays pending for the externally owned reconciliation path. This provides durable local state and deduplication boundaries; it does not claim universal exactly-once execution.

workflow_events is append-only and outbox is inserted in the same transaction as each event. Checkpoints, response bytes returned by `getReceipt`, and artifact bytes are hash checked when read; a receipt's proposed checkpoint is hash checked before recovery. These records are immutable through the store API. Checkpoint object keys are copied through null-prototype containers so keys such as `__proto__`, `constructor`, and `prototype` remain data. Repeated observations with the same source reference and contents are idempotent. A new attempt identity remains distinct, and a transport retry is a separate row under its operation attempt. The store records identities and outcomes only; it does not total expenses, settle holds, or determine whether an operation was billed.

SQLite is configured for WAL journaling, full synchronous commits, foreign-key enforcement, extension loading disabled, and a bounded lock timeout. Local storage must support SQLite WAL locking. The database path is caller supplied and must be file backed; the default repository ignore rules cover common local state files.

## Persistence versions

At the runtime-foundation introduction, database schema version 3 stored workflow revision/fence/lease, immutable checkpoint history, ordered events, transactional outbox, operation/transport attempts, source-deduplicated observations, response receipts with proposed-checkpoint integrity evidence, and immutable artifacts. Checkpoint normalization is limited to depth 128, 10,000 JSON nodes, 256 Ki UTF-16 source units across strings and keys, and 1 MiB of serialized UTF-8 JSON. It accepts data properties only, does not invoke accessors, and returns a safe typed `INVALID_INPUT` for invalid, unexpected, or oversized values on both initial-checkpoint and response-receipt writes.

At the runtime-foundation introduction, opening a version 1 database migrated it to schema version 3 in one transaction. It preserved workflow IDs, revisions, state, timestamps, and all supported text checkpoint fields—including artifact/version/approval references—inside the version 2 checkpoint envelope. It appended one migration event per workflow. Non-text, malformed, or over-limit legacy checkpoint rows aborted migration with `CHECKPOINT_CORRUPT`; all original rows, storage types, bytes, and schema were restored by transaction rollback. Opening a version 2 database added the nullable receipt checkpoint-digest column in one transaction. Existing receipts without a digest were preserved, but pending legacy receipts could not be reconciled: recovery returned `CHECKPOINT_CORRUPT` without changing workflow state, checkpoints, attempts, events, or outbox. The runtime did not invent missing integrity evidence. At that time, a database schema newer than version 3 was rejected before journal or schema writes.

The later AH-10 telemetry addition advances the current schema to version 4. Its addition is the isolated `telemetry_cursors(consumer_id, last_sequence, updated_at_ms)` table. Fresh databases create the schema-v3 workflow tables and cursor table together in one transaction. Current v1-to-v4, v2-to-v4, and v3-to-v4 upgrades are transactional: the v1 migration retains the established data-preservation and migration-event behavior, the v2 migration adds the nullable receipt checkpoint-digest column and cursor table, and the v3 migration adds only the cursor table. Existing v2 receipts without a digest remain preserved but cannot be reconciled. Failed migrations roll back schema and row changes. The current runtime rejects schemas newer than version 4 before journal-mode changes or schema writes; it does not silently downgrade or rewrite a future schema.

## Internal evidence and remaining gates

The internal tests target these implementation cases:

- **AH-01 / CON-01 — contract compatibility:** local configuration/error behavior and the internal entrypoint are tested. The shared catalog at `shared-contracts` revision `c4caaccc2ea63b273eeac17ed89af8ac64f6bbde` has no canonical generated ports or validators. Versioned valid, invalid, old-version, and unknown-field fixtures across actual producers and consumers, pinned shared release compatibility, and EI/CE conformance remain pending. ESM with `.d.ts` declarations is accepted by both supervisors; acceptance is not consumer conformance evidence.
- **Type declarations:** the internal `.d.ts` surface is checked against a small consumer fixture with pinned TypeScript 5.9.3. This verifies only this local experimental declaration surface, not a canonical contract.
- **ARC-01 — pinned assembly:** this increment has a Node 22.23.3 pin, offline lockfile/bootstrap, build/import check, tests, and CI workflow. A clean integrated release build with the canonical cross-repository revisions and deployment runtime remains pending.
- **AH-03 / AGT-02 — durable resume:** internal evidence covers a subprocess exit after receipt persistence but before checkpoint advancement, restart reconciliation with receipt checkpoint-digest verification, valid-JSON checkpoint corruption rejection with no partial state changes, strict v1 mixed-row migration rollback, v2 pending-receipt compatibility failure-closed behavior, bounded/accessor-safe checkpoint writes, before/after checkpoints, prototype-named checkpoint-key fidelity, immutable response/artifact hashes, process-level CAS, fencing, event/outbox order, cancellation from each nonterminal state, cancellation/retry and cancellation/completion races, no-retry after cancellation, completed logical-operation replay prevention, and actual Node 22 SQLite busy/locked handling. This does not execute or verify an external provider effect and is not full workflow acceptance.
- **AGT-03 — bounded recovery:** configuration parsing requires attempt, elapsed-time, and cost bounds. This increment does not orchestrate retries or enforce those limits across a workflow; later trusted-scope, planner, budget, and provider integration leaves are required.
- **ARC-02 — single data ownership:** this increment owns only private harness workflow state and documents external-reference ownership. Integrated write-path tracing and owner review remain pending.
- **FIN-01 — attempt-level metering:** attempt IDs are persisted, but there is no canonical provider/model/usage/budget-scope/correlation join or missing-data coverage report.
- **FIN-02 — duplicate observations:** the store deduplicates opaque source references locally. It does not compare direct usage with traces or prove one effective ledger charge.
- **FIN-03 — distinct billed retries:** distinct attempt IDs and separate transport retry IDs are retained, and an explicit `no_effect` permits another attempt for the same logical operation. No provider calls or cost attribution occur here, so two billed attempts and both costs are not demonstrated.
- **FIN-04 — unknown billing:** unresolved outcomes and opaque hold references survive cancellation and lease expiry. There is no conservative estimated amount, actual held-budget evidence, or canonical reconciliation result.
- **FIN-05 — estimate reconciliation:** estimated-versus-confirmed cost adjustments and linked ledger postings are not implemented.
- **BUD-01 / BUD-02 — reservations and settlement:** shared capacity reservation, spend settlement, unused-hold release, and budget projections are not implemented.
- **BUD-03 — uncertain in-flight cost:** lease expiry moves the internal attempt to unknown/reconciliation and preserves its opaque hold reference. The external hold's state and conservative amount cannot be proven by this store.
